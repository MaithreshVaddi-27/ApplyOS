# Phase 9 — Evaluation and benchmarking

> **Status:** `PROPOSED` · **Depends on:** Phases 3, 4, 5, 6 ·
> **Risks:** [R-02, R-06](../roadmap/risks.md)

---

## Outcome

The first **measured** numbers in ApplyOS's history, a committed corpus, and a CI gate that
fails when a metric moves beyond its tolerance.

---

## Why now

Every decision ApplyOS makes about a candidate's job search — reject this posting, rank that
one higher, drop this claim — is justified by a unit test proving the code matches its
contract. None of it proves the *contract* is right.

The 2026-10-09 audit found three blockers of exactly that shape. They were fixed by making the
code match the contract. Nothing measures whether the contract matches the candidate's
interest.

Evaluation is the only mechanism that closes the loop. It is also the prerequisite for Phase 10
(a dashboard over an unstable shortlist is cosmetic) and Phase 12 (publishing without
measurements means publishing an unmeasured quality claim).

## Tasks

### 9.1 — Define the corpus schema

**Deliverable.** `applyos/evals/corpus/MANIFEST.json` and a schema for the items.

```json
{
  "id": "posting-0042",
  "source": { "portal": "naukri", "url": "…", "captured": "2026-10-05" },
  "labels": {
    "keep": false,
    "flag": ["stale"],
    "labelMethod": "manual",
    "labelledBy": "maintainer",
    "rationale": "B2B SaaS role, 6+ years required; candidate is a fresher"
  }
}
```

**Requirements.**
- **Redacted.** Only the fields the evaluation needs: title, company, a paragraph of description,
  the fields the gates read. **Full third-party postings are not redistributable** and must not
  be committed.
- **Provenance per item.** Where it came from, when, and how it was labelled.
- **Label provenance is explicit.** `manual`, `candidate`, or `rule`. A label without a method
  is not usable.

### 9.2 — Build the corpus

**Deliverable.** A committed corpus covering the four boards of the market×stage matrix, and
the labelled dedupe pairs.

**Process.** A maintainer with domain knowledge:
1. Collect postings across the matrix.
2. Apply the label rubric.
3. Record the label provenance.
4. Redact to the minimum.
5. Commit with a schema version.

**Requirement.** **The corpus must not be generated by the code it evaluates.** A corpus built
by the gate implementation would trivially score 100% and prove nothing.

**Requirement.** The rubric must be written down before the labelling starts, and the rubric
itself is committed.

### 9.3 — Implement the `gates` evaluation

**Deliverable.** `applyos/evals/runners/gates.ts`.

**Metrics.** False-reject rate, false-accept rate, flag precision — overall and per gate.

**The headline metric is the false-reject rate.** A false reject costs the candidate a real
opportunity; a false accept costs them one scroll.

**Requirement.** The report shows the **distribution**, not an average. A gate that rejects 0% of
good postings and 2% of bad ones is not "99% accurate" — it rejects almost nothing, and the
average hides that.

### 9.4 — Implement the `dedupe` evaluation

**Deliverable.** `applyos/evals/runners/dedupe.ts`.

**Metrics.** Pairwise precision and recall on the labelled pairs, broken down by pair kind:
tracking variants, trailing slash, hash, multi-city spread, and near-misses.

**Requirement.** The corpus must probe all three edges of `collapseReqSpread`'s key
(`company | requisition-id`): a shared ID across companies, different IDs at one company, and a
date-shaped path segment.

### 9.5 — Implement the `documents` evaluation

**Deliverable.** `applyos/evals/runners/documents.ts`.

**Metrics.** Ungrounded-claim rate, gap preservation, page-budget compliance, ATS extractability.

**Dependency.** The Document Manifest from Phase 6. Without it, "grounded" is a model judgement
with nothing to check.

**Known limitation, recorded not hidden.** The manifest records what the generator *believed* it
sourced. It does not independently verify that the sourced profile entry says what the claim
says. A future evaluation could sample claims for a semantic check.

### 9.6 — Implement the `ranking` evaluation

**Deliverable.** `applyos/evals/runners/ranking.ts`.

**Metrics.** Spearman ρ between two runs, top-k overlap, band churn, per-posting score σ.

**Purpose.** Quantify the difference between the model-driven and the deterministic ranker. The
spec's own guidance says *"±5 pts is noise; only band changes are signal"* — this is how that
claim gets checked.

### 9.7 — Establish the baselines

**Deliverable.** `applyos/evals/baselines/*.json` with real values.

**Process.**
1. Run each evaluation on the corpus.
2. Record the measured metrics.
3. Set a tolerance with a deliberate margin — a zero tolerance would fail CI on every unrelated
   change.
4. Commit the baseline.

**Requirement.** `docs/engineering/evaluation.md`'s `null` placeholders are replaced with the
real numbers, and the document's "no metric is measured" caveat is removed.

### 9.8 — Add the CI gate

**Deliverable.** A CI job that runs the evaluations and fails on a tolerance breach.

**Requirement.** The job is green from the first run, and its runtime is small enough to sit on
every PR. A target of under 30 seconds is proposed in
[../engineering/performance.md](../engineering/performance.md#6-proposed-budgets) and is itself
`PROPOSED` until measured.

### 9.9 — Add the `eval` command

**Deliverable.** `applyos eval [suite] [--format …] [--update-baseline]`.

**Requirements.**
- `--update-baseline` is a maintainer action and is documented as such.
- The command exits 1 when a metric is outside its tolerance.
- It never touches the network.

### 9.10 — Publish the numbers

**Deliverable.** `docs/engineering/evaluation.md` updated with the measured values, and the
`CHANGELOG.md` entry.

**Requirement.** Every published number cites the corpus hash and the model version, so a
reader can tell exactly what was measured.

## Acceptance criteria

- [ ] A corpus exists, is committed, is redacted, and has provenance per item.
- [ ] The label rubric is written and committed.
- [ ] The corpus was not generated by the code it evaluates.
- [ ] Four evaluations exist: gates, dedupe, documents, ranking.
- [ ] Every evaluation runs offline and deterministically.
- [ ] Baselines exist with real measured values.
- [ ] A CI job runs the evaluations and fails on a tolerance breach.
- [ ] `applyos eval` exists and exits 1 on a breach.
- [ ] `docs/engineering/evaluation.md` publishes the numbers with the corpus hash.
- [ ] The whole suite is green on three operating systems.

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| The corpus is too small to mean anything | medium | medium | A minimum size per board and per label class is stated in the corpus README; the metric's confidence interval is reported |
| The labels are subjective and wrong | high | medium | Label provenance is recorded per item; disagreements are recorded rather than smoothed; the rubric is committed |
| The corpus is built to flatter the implementation | low | critical | The rubric is written before labelling; the corpus is committed for review; **the corpus must not be generated by the evaluated code** |
| A metric moves and the tolerance is too tight | medium | medium | Tolerances are set with a deliberate margin after the first measurement |
| The evaluation is slow and blocks every PR | medium | medium | The runtime target is measured in Phase 9; if it is too slow, the heavy suites run nightly and the fast ones gate every PR |

---

## Rollback

| Change | Rollback |
|---|---|
| The corpus | Delete the directory; the evaluations report "no corpus" and pass |
| A runner | Remove it; the CI job runs the remaining suites |
| The CI gate | Make it non-blocking; the baselines still record the numbers |
| The tolerance | Loosen it with a recorded reason |
